# Native Termux commands

The bridge uses Termux's official `RUN_COMMAND` service with a direct executable, argument array, optional working directory and stdin, always in background mode. It opens no terminal UI and assumes no Codex installation or login. Termux 0.109 or newer, the owner's Android `com.termux.permission.RUN_COMMAND` grant, and `allow-external-apps=true` in Termux's own configuration are required. SIConnect never edits that private configuration. [Official setup and API](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent).

`termux.status` reports actual package identity and permissions. External-app policy and successful commands are timestamped callback observations bound to the current UID, version and first-install time. Remote diagnostics/results are scoped to the requesting agent. The owner setup panel can run explicit harmless identity and Codex sign-in checks through normal owner approval.

`termux.execute` takes an absolute `executable`, exact `arguments`, optional absolute `cwd` and `stdin`, `timeoutMs` up to 120,000 and `maxOutputBytes` up to 32,768 per stream. The existing arbitrary-shell approval policy applies to the canonical argv/cwd/stdin. Execution uses the Termux Android app UID, distinct from SIConnect and privileged shell. Timeout limits waiting; the API provides no verified command termination contract.

Before IPC, a separate SQLite journal records the original engine request ID and a random callback nonce. The explicit, package-bound, nonexported receiver uses a one-shot mutable PendingIntent: Termux supplies results through its fill-in Intent, which an immutable token would discard. No routing fill-in flags are allowed. Callback fields are validated and output is bounded before commit; the waiter is resumed only after that commit. [Termux result sender](https://github.com/termux/termux-app/blob/master/termux-shared/src/main/java/com/termux/shared/shell/command/result/ResultSender.java), [Android PendingIntent mutability](https://developer.android.com/reference/android/app/PendingIntent#FLAG_IMMUTABLE).

`termux.result(executionId)` reads only the caller's durable journal. `termux.recent` discovers own execution IDs in pages of up to 50 metadata rows, optionally unresolved only; it exposes no command text, output or nonces. Late callbacks survive SIConnect process death, cancellation and wait expiry without replaying commands or rewriting terminal core request history. At most four requests wait concurrently and 64 recent unresolved dispatches are admitted. A dispatch whose deadline passed more than 15 minutes ago stops counting toward that limit, so commands that never call back (servers, a force-stopped Termux) cannot lock out Termux permanently; it remains `DISPATCHING`, inspectable and able to record a late callback. Unresolved evidence is never aged out. Owner-enabled payload retention may remove stdout/stderr/raw error text only when the original core request is known terminal and is not `UNKNOWN_OUTCOME`; callback identity, exit/error codes, success metadata and explicit `payloadExpired` remain. Metadata is not automatically deleted.

## Codex npm launchers

A background Termux process may lack the interactive termux-exec path shim. A launcher whose shebang names /usr/bin/env can fail with exit 126 even though Codex works in the terminal. For npm JavaScript entrypoints, use Termux's node executable with the script path as its first argument; the owner saved-sign-in check handles that route. Standalone/custom native launchers remain supported. Saved sign-in is not a verified model request, and TLS/DNS configuration belongs to the owner's existing Termux environment. Authentication output is never printed by the owner check.

## Noninteractive Codex execution — build 27

`codex.execute` is a production native launcher through the existing Termux bridge. Build-27 host, native policy and real authenticated model/command checks pass; see [pass 22](engineering-pass-22.md). The earlier saved-login check established CLI-reported sign-in with Codex 0.167.0 through Node, not a successful model request or valid live credentials. No official Android compatibility claim follows from that check.

The caller supplies exactly one known absolute `nodeEntrypoint` for the installed npm JavaScript launcher or `androidCompatibilityLauncher` for an explicitly selected existing script, an existing absolute `cwd` and a nonblank `prompt` of at most 8,192 characters. Optional `profile` selects an existing owner profile; `allowOutsideGitRepository=true` explicitly adds `--skip-git-repo-check`. The launcher loads the existing Termux login environment with startup output suppressed, then restores the real command stdout/stderr and invokes fixed Termux Node for JavaScript or fixed Termux sh for the compatibility script. The prompt remains one literal argument after `--`; no prompt text is interpolated into a shell program. Stdin is closed and the special `-` prompt is rejected. No interactive terminal is opened.

Each fresh run uses `codex exec -c 'approval_policy="never"' --sandbox danger-full-access --json`. These are per-invocation settings: the launcher does not modify saved CLI configuration, credentials, model choice, MCP servers or existing sessions. It does not resume another session, bypass hook trust, ignore owner rules/configuration or silently retry. Existing configured profiles, rules and trusted hooks remain applicable. Codex normally saves its own session; the launcher does not request `--ephemeral`. Official references: [noninteractive mode](https://learn.chatgpt.com/docs/non-interactive-mode), [CLI options](https://learn.chatgpt.com/docs/cli/reference), [approval configuration](https://learn.chatgpt.com/docs/config-file/config-reference).

The no-approval/sandbox settings express the authorized workflow's Codex access; they do not bypass SIConnect policy. `codex.execute` submits a real same-agent `termux.execute` child with the original deadline, deterministic child identity and unchanged origin. Both capabilities and the existing arbitrary-shell policy must permit execution. A Custom profile may still require owner review of the actual child; approving the parent does not approve the child. A previously owner-enabled Full control profile covers available ordinary remote capabilities according to its saved policy without changing other agents. Android app UID, filesystem permissions, SELinux, platform prompts and protected owner controls still apply. Removing Codex sandbox restrictions does not prove that Android supports Linux bubblewrap or that every command can run.

The response exposes the exact `executionId`/child state and any retained native result. `awaitingApproval=true` is a real pending child, not successful execution. Use `termux.result` with that same ID for late completion; never resubmit an uncertain run. Waiting is bounded to at most 120 seconds and does not guarantee the subprocess stopped. JSONL events and stdout/stderr are bounded to 32,768 bytes per stream; inspect truncation and native errors. A native exit, callback or `turn.completed` event is not independent proof of all requested file/app/network effects; `taskOutcomeVerified` remains false.

### Codex execution is separate from phone MCP access

The inspected phone Codex MCP configuration contained **zero servers**. Launching Codex natively therefore does not establish a Codex-to-SIConnect phone connection. `codex.execute` reports `phoneControlConnectionVerified=false`; it does not pair a client, reuse another bot's credential or configure an MCP server. Existing ChatGPT/Grok connections remain separate identities. Any later Codex phone-control setup must use an explicit real connection and verify its own discovery/execution. A real model request and shell command now pass using the explicit full-access compatibility route. The separate phone-control connection remains **PENDING**; creating its dedicated identity requires genuine owner authentication in SIConnect’s Agents → Pair agent flow.

### Tested Android compatibility launcher

The reviewed `tools/termux/codex-siconnect-android.sh` is bundled as `assets/codex-siconnect-android.sh`. It requires the owner’s existing Termux `proot`, Node, Codex npm installation, readable DNS file and trusted CA bundle. It binds Termux’s `etc/resolv.conf` to `/etc/resolv.conf`, preserves an existing `SSL_CERT_FILE` or selects Termux’s trusted `etc/tls/cert.pem`, and launches Node explicitly to avoid the npm shebang failure. TLS verification stays enabled. It neither installs dependencies nor changes PATH, global configuration, credentials or existing launchers.

On the accepted test phone the exact script was explicitly installed without overwriting differing files at `/data/data/com.termux/files/home/.siconnect/bin/codex-android`. Pass that path as `androidCompatibilityLauncher`, omitting `nodeEntrypoint`. APK updates bundle the asset but do not install/execute the script automatically. The first direct-Node model run’s late failure is retained; it was not replayed. The compatibility run’s actual command output verified the Termux UID and unique marker with native exit 0 and completed model turn in 10.04 seconds. This is acceptance on the tested device, not an official Android-support claim or a universal latency guarantee.
