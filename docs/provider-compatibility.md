Grok Bot reported that its saved connector launches `mcp-remote` in its cloud environment and reads the token from its secure secret store. The Mac does not host that relay. Its first two direct gateway checks were distinguished from a subsequent invocation through its saved connector. Do not equate Grok Bot's Cloudflare management plugin with the SIConnect phone connector.

The endpoint supports OAuth and the existing private bearer mode. Official SDK OAuth authorization/PKCE/refresh/tool invocation passes locally; this is separate from hosted-client onboarding. The app independently hashes/authenticates the forwarded agent credential and applies the current local grant. A compromised gateway that sees that credential can impersonate it; independent agent signatures are not implemented.

Client identity matters: two existing OAuth connections had the same display name. App permission was enabled on one while the other made the denied request. The owner subsequently used the new exact-request permission screen to enable the intended connection; SQLite confirmed both Apps scope and the deliberate broad-shell choice. The installed UI distinguishes same-name agents and offers a permission-review card bound to the exact denied request's authenticated agent. An agent-scope denial is final for that request; it does not create an approval. After an owner grant change, submit a new request. Do not reconnect or duplicate the plugin to solve a local permission problem.

The Cloudflare management connector manages cloud resources. It does not grant permission to control the phone. SIConnect is its own MCP resource, and each client has to authenticate to that resource. The current Grok/Hermes private-bearer setup shares an agent; OAuth Dots connections have separate local grants. Sharing an endpoint never implies sharing permissions.

Following the owner grant correction, the actual Dots conversation completed an official Play Store app installation. Phone records correlated the check, listing launch, single install action and final bounded verification to that OAuth identity. An independent user-0 query confirmed package/version/installer. The separate Dots self-addressed email test subsequently completed, with send and Sent/header/body verification correlated against phone records and an independent Gmail UI read. Dots also uninstalled the designated test app after actual owner approval; removal was independently verified. This does not establish every provider/tool combination or background lifecycle guarantee.

Pass 3 preserves the existing endpoint, OAuth resources and private bearer credentials. The local official-SDK regression suite now includes socket replacement: old in-flight ownership returns an explicit unknown outcome, a new socket is offline until hello completes, and a subsequent call succeeds. Pending approval results include machine-readable guidance to retrieve the same request via `requests_get`. Historical Grok/Dots/Hermes actions are not automatically rerun by this suite.

Hermes was freshly verified after the gateway deployment using its actual global MCP configuration: status, shell identity and detailed package metadata succeeded. A subsequent owner-coordinated locked-phone workflow retrieved a completed request after a real connection replacement, performed disposable shell-file operations and scheduled/verified exact reminder delivery. The final phone state remained screen off/device locked. This is native MCP runtime evidence, not a claim that a new full autonomous Hermes conversation completed. Dots/Grok historical successes and existing credentials are preserved; their full current application UX has not been rerun in this increment. Local OAuth SDK tests do not substitute for a fresh Dots UI test.

The legacy Grok/Hermes bearer configuration shares one device principal; it therefore cannot provide independent per-client revocation. Moving each client to its own explicit pairing is future owner-coordinated work. The existing live credentials were preserved during this pass.


Pass 4 found a distinct provider configuration issue: the Telegram-facing Hermes profile had no MCP servers even though the global Hermes profile worked. The existing SIConnect HTTP configuration and existing credential reference were added to the intended profile without changing its other settings or phone grants. A supported live profile rescan succeeded, and calls through that exact profile returned successful device status and privileged shell identity. The subsequent real Grokbot → Telegram → Hermes → phone chain completed: status, battery, privileged identity, package inspection and one disposable notification all succeeded and matched durable device records. The final Hermes reply was persisted. Hermes selected the older raw package-inspection tool rather than the requested compact inspection, so this is not claimed as a compact-tool efficiency success. A notifications-list attempt was denied by the existing local scope; credentials/grants were not broadened. Credentials and profile-specific private names are not part of this repository. When diagnosing Hermes, check the active routed profile rather than assuming the global config applies to every bot.
