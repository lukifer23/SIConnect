## Control-center and connection refresh

- The phone package had been disabled and stopped; it had not been uninstalled. It was re-enabled and updated using its existing matching certificate. The reason Android disabled it was not established.
- Expanded Home uses separate connection/readiness and attention/agent columns. Agents, Settings, Activity and automation forms use dedicated split layouts on the unfolded Fold. Compact layouts remain available; large text falls back to a readable single pane.
- Settings groups access, connections, folders, background timing, appearance, commute/weather, history, private workspaces and developer tools into focused pages. Category state and unsaved forms are retained. Diagnostic export uses Android’s save-document picker, and workspace checks invoke real device capabilities.
- Activity selection retains only its request identity across recreation and reloads actual records. Closing, section changes and approval notifications invalidate pending inspection. Each request has independent scroll/expansion state. Agent deep links are consumed after selection; recovery setup and connection dialogs survive recreation without saving secrets in Android instance state.
- The existing Grok Bot connector reports Connected with **101 tools**. Dots retains its Primary OAuth account and exposes **101 tools** (**47 write / 54 read**) after refreshing its old catalog. No new identities, reauthentication or credential rotation was needed.
- Real hosted MCP checks passed native status, battery, memory, storage, network and thermal reads, plus actual shell UID 2000. These are phone execution results through the existing gateway, not a simulated device peer.
- Database integrity and readback preserve all five original agent identities and credentials, three reminders, two automations and the selected folder. Initial restoration left grants unchanged. At the owner’s subsequent request, the exact Dots identity behind a denied Google Messages request received the private-workspace family and app/backend-bound Google Messages allowances through Android owner authentication.
- Full control is an explicit per-agent owner-authenticated profile. It persists in SQLite without a grant expiry and removes SIConnect per-action approvals, including critical classifications. Disabling restores the saved custom profile. Revocation, remote emergency controls, Android access/availability, protected native surfaces and local-owner-only operations remain enforced. Its review lists current waiting work; an explicit continuation reuses eligible original request IDs and never replays expired, cancelled or other terminal actions. The owner activated this code-23 profile for the existing Dots identity. Actual subsequent private Clock calls executed without new SIConnect approvals, started a 19-minute timer, and stopped it via a notification action; the owner confirmed the timer stopped. Google Messages opened and exposed six verified messages, but semantic scroll dispatch did not reveal the earlier messages. Full-profile rollback fixtures passed; the explicit pending-continuation device fixture now passes with bounded real backend readiness.
- Denied private-app requests offer a direct owner-confirmed setup action. Enabling the family and selected app uses one SQLite transaction through the existing validated owner setters. Agent writes now reject SQLite’s `-1` failure result, so a failed second write cannot report success or leave a partial permission change. Private captures and client evidence remain outside Git.

The new physical batch passed nine cases and skipped one pending-continuation case because its initial backend-readiness check raced daemon reattachment; the fixture now waits for real readiness and passes in the code-24 follow-up. The navigation/recreation and retention-cancellation UI checks run against the physical phone; earlier harness failures are retained privately rather than counted as passes. Android instrumentation can leave Accessibility enabled but disconnected, so final readiness must be checked in the normal app process. This UI refresh does not complete the broader battery, provider, network and reboot acceptance matrix below.

## Current blockers and acceptance gaps

- The private UI mechanism passed on code 19 with an awake, unlocked phone through ADB_SERVICE. Code-21 private caller/backend death, queued-open cancellation and revocation checks now pass on the awake/unlocked phone. This Samsung build keeps ordinary virtual displays in physical power group 0. Locked/off UI needs legitimate companion/OEM ComputerControl provisioning and acceptance; extra manifest permissions alone do not solve it. No wake/unlock/shared-screen fallback is used. Wider app compatibility, optional Shizuku execution and actual owner UI/authentication lifecycle remain open.
- The real tomorrow-weather read/decision path succeeded after owner-supplied coordinates; a rain reminder was correctly skipped. Commute settings, consent-aware native location and actual Maps route-reading capabilities are now implemented. Maps UI control produced a real future-morning duration range; native GPS still requires owner consent, and Grok completed future-time selection and the corrected route using existing shell permission; the installed native reader also passed its physical check. New native-family scopes are still explicit owner choices. Tool metadata now distinguishes a point forecast, caller-owned reminders and the next Android-exposed alarm.

- The real unplugged native health/cooldown case passed on code 20 using actual readings and a clearly labeled disposable notification. Wider warning/recovery and lifecycle behavior remains separate acceptance.
- Calendar writes require a verified dedicated writable test calendar. No personal calendar was selected or changed in this pass.
- Biometric success/cancel, special-access restoration and disruptive network/reboot scenarios need their actual owner/platform conditions. Instrumentation force-stop is separate from ordinary process death.
- Hosted retry identity is deployed and verified with actual reads/writes and a single recorded execution. Grok also returned a successful stable keyed identity; its initial negative interpretation was incorrect. Review the exact results and remaining loss/restart limits in pass 14. The initial Grok status read recovered its successful original record after socket replacement; a shell attempt failed before phone dispatch.
- Opt-in execution retention is implemented in code 18 and protects active/uncertain work. Compact identities and notification/slot claims remain permanent; hard quotas, Inbox archival and real workload/cleanup profiling remain open. Blocking IO cancellation and ADB per-packet flow control are patched in code 15; their full physical interruption acceptance remains open. Shared discovery and network-triggered wake-up are implemented; broader performance and transition acceptance remain open.
- Full Fold/large-font UI acceptance, quiet CPU/PSS/network/database-growth measurements and compatible signed distribution remain incomplete. There is no completed battery or 24-hour availability study.
